Ligando o JVExplorer no seu ambiente

A lista de módulos, as classes e o painel Onde é usado nesta tela são reais: saíram do cruzamento de TSIBTA, TSIEVP e TSIAAG — 30 módulos, 102 classes, 105 vínculos. O que ainda não está aqui é o corpo dos arquivos, que mora no BLOB de TSIJAR. O módulo 36 é a exceção: o jar dele foi lido de verdade, e é o que o visualizador mostra.

1. O modelo de dados (confirmado)

O bytecode do botão BaixarJAR entrega o mapa inteiro:

ModuloAdicional          -- entidade do módulo, PK = CODMODULO
   └── ArquivoModulo     -- coleção filha (tabela TSIJAR)
         DESCRICAO       -- nome do arquivo, ex. "MODULO-SNK-1.0.JAR"
         ARQUIVO         -- BLOB com os bytes do jar

Em Java isso é literalmente:

DynamicVO modulo = (DynamicVO) dwf.findEntityByPrimaryKeyAsVO("ModuloAdicional", codModulo);
Collection<DynamicVO> arquivos = modulo.asCollection("ArquivoModulo");
byte[] conteudo = arquivo.asBlob("ARQUIVO");

Nenhum SQL montado na mão, nenhum nome de tabela chutado. O JVExplorer usa o mesmo caminho.

2. Falta confirmar os nomes das colunas

Os CSVs vieram sem cabeçalho. Uma consulta resolve:

SELECT TABLE_NAME, ORDINAL_POSITION, COLUMN_NAME, DATA_TYPE
  FROM INFORMATION_SCHEMA.COLUMNS
 WHERE TABLE_NAME IN ('TSIJAR','TSIBTA','TSIEVP','TSIAAG')
 ORDER BY TABLE_NAME, ORDINAL_POSITION;

E a tabela-cabeçalho do módulo (a que ModuloAdicional mapeia):

SELECT TABLE_NAME FROM INFORMATION_SCHEMA.COLUMNS
 WHERE COLUMN_NAME = 'CODMODULO';

3. O backend: JVExplorerSP

Um módulo Java importado como qualquer outro, expondo três leituras:

@Service(serviceName = "JVExplorerSP",
         transactionType = TransactionType.NotSupported)
public class JVExplorerService {

    public List<ModuloDTO>  listarModulos();
    public List<ArquivoDTO> listarArquivos(BigDecimal codModulo);
    public FonteDTO         lerArquivo(BigDecimal codModulo, String path);
}

lerArquivo abre o jar em memória com JarInputStream: se a entrada for .java, devolve o texto; se for .class, o CFR reconstrói o fonte a partir do byte[]. Nada é gravado em disco. NotSupported executa fora de transação, que é o correto para leitura pura.

O CFR precisa estar no classpath do módulo — o caminho mais simples é despejar as classes dele dentro do próprio jar do JVExplorer na hora de exportar.

4. Onde a tela mora

O seu app HTML5 de estoque já mostra o caminho: um index.jsp com <snk:load />, ${BASE_FOLDER} nos assets e consulta direto no banco:

<snk:query var="modulos">
   SELECT M.CODMODULO, M.DESCRICAO, A.DESCRICAO NOMEARQ,
          DATALENGTH(A.ARQUIVO) TAMANHO
     FROM <TABELA_MODULO> M
     LEFT JOIN TSIJAR A ON A.CODMODULO = M.CODMODULO
    ORDER BY M.CODMODULO
</snk:query>

<c:forEach items="${modulos.rows}" var="row"> … </c:forEach>

Ou seja: a listagem não precisa de serviço nenhum — sai do JSP. O serviço entra só para o BLOB e a descompilação, que o snk:query não resolve.

5. Alternativa sem @Service

Se o SDK do ambiente não tiver a anotação @Service, dá para reaproveitar o truque que o seu botão de download já usa: SessionFile.createSessionFile(nome, tipo, bytes), guardado com putHttpSessionAttribute e servido por /mge/visualizadorArquivos.mge?chaveArquivo=…. Trocando application/zip por text/plain, o mesmo mecanismo entrega o fonte descompilado para um <iframe> da tela. Menos elegante, zero infraestrutura nova.

6. Cache

Descompilar o jar a cada clique é caro. O serviço guarda o resultado por módulo em memória, com a data de alteração do registro como chave — jar reimportado invalida o cache sozinho.
